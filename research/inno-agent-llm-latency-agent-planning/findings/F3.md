# F3: Ollama Latency Sources and Behavior

## Findings

### [1] Ollama serializes model loading to one at a time — only one model load can occur concurrently, but requests to already-loaded models can run in parallel
- quote: "We can only load one model at a time but new requests to models that already loaded can happen in parallel"
- url: https://raw.githubusercontent.com/ollama/ollama/refs/heads/main/server/sched.go
- source_type: primary
- published: 2025-07 (current main branch)
- confidence: high

### [2] Default queue size is 512; exceeding it returns HTTP 503 with "server busy"
- quote: "If too many requests are sent to the server, it will respond with a 503 error indicating the server is overloaded. You can adjust how many requests may be queued by setting OLLAMA_MAX_QUEUE."
- url: https://docs.ollama.com/faq
- source_type: primary
- published: 2025-07-25
- confidence: high

### [3] Default context length auto-scales by VRAM tier: <24 GiB → 4K, 24-48 GiB → 32K, ≥48 GiB → 256K tokens
- quote: "Ollama defaults to the following context lengths based on VRAM: < 24 GiB VRAM: 4k context; 24-48 GiB VRAM: 32k context; >= 48 GiB VRAM: 256k context"
- url: https://docs.ollama.com/context-length
- source_type: primary
- published: 2025-07-25
- confidence: high

### [4] Parallel requests multiply context memory: OLLAMA_NUM_PARALLEL (default 1) × OLLAMA_CONTEXT_LENGTH determines VRAM consumed by KV cache
- quote: "Parallel request processing for a given model results in increasing the context size by the number of parallel requests. For example, a 2K context with 4 parallel requests will result in an 8K context and additional memory allocation."
- url: https://docs.ollama.com/faq
- source_type: primary
- published: 2025-07-25
- confidence: high

### [5] After model unload, Ollama waits up to 5 seconds for GPU VRAM recovery before loading the next model — polling every 250ms until 75% of estimated VRAM is reclaimed
- quote: "Free memory reporting on GPUs can lag for a while even after the runner exits, so we have to keep checking until we see the available memory recover... typical convergence is 0.5-1.5s"
- url: https://raw.githubusercontent.com/ollama/ollama/refs/heads/main/server/sched.go
- source_type: primary
- published: 2025-07 (current main branch)
- confidence: high

### [6] Models stay loaded in GPU memory for 5 minutes by default (OLLAMA_KEEP_ALIVE), after which they are unloaded — first request to an unloaded model incurs cold-start load latency
- quote: "By default models are kept in memory for 5 minutes before being unloaded. This allows for quicker response times if you're making numerous requests to the LLM."
- url: https://docs.ollama.com/faq
- source_type: primary
- published: 2025-07-25
- confidence: high

### [7] When model options change (context size, adapters, etc.) the entire model must be unloaded and reloaded — this triggers full cold-start latency even for already-running models
- quote: "if runner.needsReload(ctx, pending) ... runnerToExpire = runner"
- url: https://raw.githubusercontent.com/ollama/ollama/refs/heads/main/server/sched.go
- source_type: primary
- published: 2025-07 (current main branch)
- confidence: high

### [8] Default loaded model cap is 3 × number of GPUs (OLLAMA_MAX_LOADED_MODELS); exceeding this evicts the least-recently-active model
- quote: "OLLAMA_MAX_LOADED_MODELS - The maximum number of models that can be loaded concurrently provided they fit in available memory. The default is 3 * the number of GPUs or 3 for CPU inference."
- url: https://docs.ollama.com/faq
- source_type: primary
- published: 2025-07-25
- confidence: high

### [9] Streaming uses NDJSON (newline-delimited JSON) with per-token flush — each chunk is a full response object written with `c.Writer.Write(append(data, '\n')); c.Writer.Flush()`
- quote: (confirmed from routes.go source: `streamResponse(c, ch)` and the generate handler: `data, err := json.Marshal(resp); c.Writer.Write(append(data, '\n')); c.Writer.Flush()`)
- url: https://raw.githubusercontent.com/ollama/ollama/refs/heads/main/server/routes.go
- source_type: primary
- published: 2025-07 (current main branch)
- confidence: high

### [10] OOM during load triggers a one-shot retry path that reduces auto context size or evicts all other models — this is a significant latency spike for marginal-VRAM scenarios
- quote: "if !req.oomRetryAttempted && llm.IsOutOfMemory(err) { ... req.oomRetryAttempted = true; slog.Warn("llama-server load failed; reducing automatic context and retrying once" ...) }"
- url: https://raw.githubusercontent.com/ollama/ollama/refs/heads/main/server/sched.go
- source_type: primary
- published: 2025-07 (current main branch)
- confidence: high

### [11] GPU placement prefers single-GPU fit over multi-GPU spread to avoid PCI bus transfer overhead — multi-GPU only when model doesn't fit on any single GPU
- quote: "When loading a new model, Ollama evaluates the required VRAM for the model against what is currently available. If the model will entirely fit on any single GPU, Ollama will load the model on that GPU. This typically provides the best performance as it reduces the amount of data transferring across the PCI bus during inference."
- url: https://docs.ollama.com/faq
- source_type: primary
- published: 2025-07-25
- confidence: high

### [12] The scheduler processes pending requests sequentially in a single goroutine (processPending), meaning one slow scheduling decision blocks all subsequent requests
- quote: (confirmed from sched.go: single `processPending` goroutine reads from `pendingReqCh` channel and processes one request at a time)
- url: https://raw.githubusercontent.com/ollama/ollama/refs/heads/main/server/sched.go
- source_type: primary
- published: 2025-07 (current main branch)
- confidence: high

## Dead ends
- WebSearch tool was unavailable in this environment; all research relied on direct URL fetching
- GitHub code search API requires authentication (401); could not search for streaming implementation by function name
- Ollama's streaming implementation file (stream.go or similar) was not found at expected paths — streaming logic is inlined in routes.go handlers
- No formal latency benchmarks or profiling documentation exists in Ollama's official docs

## Suggested follow-ups
- Measure actual TTFT (time-to-first-token) and inter-token latency across model sizes and context lengths to establish baseline numbers for comparison with vLLM
- Investigate how Ollama's llama.cpp backend implements continuous batching (or lack thereof) vs vLLM's PagedAttention scheduler — this is likely the largest throughput difference
- Quantify the cold-start load time for common model sizes (7B, 13B, 70B) on typical GPU hardware to understand the reload penalty
