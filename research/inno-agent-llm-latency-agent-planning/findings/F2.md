# F2: vLLM Performance Internals — Latency Diagnostic Reference

## 1. Request Lifecycle Phases

### Prefill Phase
**What**: Processing the entire input prompt through all transformer layers to compute KV cache entries. This is the "input processing" step.

**Latency impact**: Dominates TTFT (Time to First Token). Scales linearly with prompt length in tokens. With 1000 input tokens, prefill is ~1000x slower than a single decode step.

**Key metrics**:
- `vllm:request_prefill_time_seconds` (Histogram) — time in prefill
- `vllm:time_to_first_token_seconds` (Histogram) — TTFT includes queue wait + prefill
- `vllm:request_prefill_kv_computed_tokens` (Histogram) — new KV tokens computed (excludes cached)

**Latency diagnosis**:
- High TTFT but low ITL → prefill bottleneck
- Check `kv_cache_usage_perc` — if near 1.0, prefill is being delayed
- Long prompts (RAG contexts, multi-turn) cause prefill spikes
- Use prefix caching to skip redundant prefill of repeated prefixes

### Decode Phase
**What**: Generating tokens one at a time. Each step runs the full model forward but only processes 1 new token (with KV cache for all previous tokens).

**Latency impact**: Determines ITL (Inter-Token Latency). Scales with model size and batch size (not sequence length, thanks to paged attention).

**Key metrics**:
- `vllm:request_decode_time_seconds` (Histogram) — total decode time
- `vllm:inter_token_latency_seconds` (Histogram) — time between tokens
- `vllm:request_time_per_output_token_seconds` (Histogram) — per-token decode cost

**Latency diagnosis**:
- High ITL → decode bottleneck
- Check `num_requests_running` — more concurrent requests = higher ITL
- GPU compute saturation: decode is memory-bandwidth bound for most models
- Speculative decoding can reduce ITL at low-to-medium QPS

## 2. Scheduler & Continuous Batching

**What**: vLLM V1 scheduler runs a busy loop in the EngineCore process, continuously scheduling requests and dispatching work to GPU workers. It implements **continuous batching** — new requests can join an active batch between decode steps (no need to wait for all requests in a batch to finish).

**Latency impact**: Continuous batching prevents head-of-line blocking. A slow request doesn't block others. However, high batch occupancy increases ITL for all requests in the batch.

**Key metrics**:
- `vllm:num_requests_running` (Gauge) — requests currently in batch
- `vllm:num_requests_waiting` (Gauge) — requests in queue
- `vllm:num_requests_waiting_by_reason` (Gauge) — breakdown: 'capacity' vs 'deferred'
- `vllm:request_queue_time_seconds` (Histogram) — time waiting before scheduling
- `vllm:num_preemptions` (Counter) — requests preempted to free KV cache

**Latency diagnosis**:
- High queue time → insufficient capacity (too many requests or too little KV cache)
- `num_preemptions` increasing → KV cache exhaustion causing request re-scheduling
- Check `waiting_by_reason` labels: 'capacity' = need more resources, 'deferred' = LoRA/KV transfer constraints
- Preemption during decode is particularly expensive: the request re-enters prefill from scratch

**Architecture** (V1):
- 1 EngineCore process per data parallel rank runs the scheduler
- 1 API server process per DP rank handles HTTP/tokenization
- 1 GPU worker process per GPU executes model forward passes
- Total processes = API servers + Engine Cores + GPU Workers + (1 DP coordinator if DP>1)

## 3. Paged Attention

**What**: Memory management technique that stores KV cache in fixed-size blocks (pages) on GPU, analogous to OS virtual memory. Blocks can be non-contiguous in physical GPU memory. vLLM maintains a block table mapping logical → physical blocks.

**Latency impact**: Enables memory-efficient batching (no pre-allocation of max_seq_len per request). Eliminates memory fragmentation. Default block size is 16 tokens.

**Key design points**:
- KV cache stored as separate K and V blocks: `[num_blocks, num_kv_heads, head_size, block_size]`
- Blocks only fully allocated (no partial blocks)
- Block size affects granularity of memory reuse and prefix cache efficiency
- The paged attention kernel (`paged_attention_kernel`) processes one query token against blocks of key/value tokens using thread groups for memory coalescing

**Metrics**:
- `vllm:kv_cache_usage_perc` (Gauge) — fraction of KV cache blocks in use (0–1)
- `vllm:kv_block_lifetime_seconds` (Histogram) — how long a sampled block lives (allocation → eviction)
- `vllm:kv_block_idle_before_evict_seconds` (Histogram) — idle time before eviction
- `vllm:kv_block_reuse_gap_seconds` (Histogram) — time between consecutive block touches

**Latency diagnosis**:
- `kv_cache_usage_perc` > 0.9 → high risk of preemption and request queuing
- High block lifetime → requests holding cache too long (long sequences or high batch)
- High idle before evict → cache waste (blocks allocated but not actively used)
- Increase `gpu_memory_utilization` if GPU memory isn't fully used
- Reduce `max_model_len` to allow more concurrent requests

## 4. Automatic Prefix Caching (APC)

**What**: Caches KV blocks of processed requests so new requests sharing the same prefix can skip re-computing those blocks. Uses a hash-based approach: each block is hashed by (parent_hash, token_ids, extra_hashes) with SHA-256 by default (v0.11+).

**Latency impact**: Dramatically reduces TTFT for workloads with shared prefixes (system prompts, RAG documents, multi-turn conversations). Can reduce prefill to near-zero for cached portions.

**Key metrics**:
- `vllm:prefix_cache_queries` (Counter) — total token queries to cache
- `vllm:prefix_cache_hits` (Counter) — cache hits
- Hit rate = `rate(cache_query_hit[5m]) / rate(cache_query_total[5m])` in Prometheus
- `vllm:request_prefill_kv_computed_tokens` — actual new tokens computed (lower = more cache hits)

**Configuration**:
- Enable: `--enable-prefix-caching` (default: enabled in V1)
- Hash algorithm: `--prefix-caching-hash-algo` (sha256, sha256_cbor, xxhash, xxhash_cbor)
- Cache isolation: `cache_salt` parameter in request JSON

**Latency diagnosis**:
- Low hit rate with shared prefixes → check if prompts differ at token level
- Block size mismatch: only full blocks cached. With block_size=16, first 16 tokens must match exactly
- Multi-modal inputs: image hashes are extra hash components — same image URL needed
- APC only helps prefill, not decode. If decode dominates (long outputs), APC has minimal impact
- Use `xxhash` for faster hashing if security isn't a concern

## 5. Speculative Decoding

**What**: Uses a smaller/faster "draft" model to propose multiple candidate tokens, then validates them all in parallel with the target model. Accepted tokens are kept; rejected ones cause re-sampling from the target distribution. Guarantees lossless output (same distribution as non-speculative).

**Latency impact**: Reduces ITL by generating multiple tokens per forward pass. Most effective at low-to-medium QPS where the GPU isn't fully utilized. Trade-off: draft model adds memory overhead and compute during validation.

**Methods supported**:
| Method | Best for | Notes |
|--------|----------|-------|
| EAGLE | General purpose | High gain at low QPS |
| MTP | Models with native MTP support | Best when model supports it |
| Draft Model | Latency-focused | Needs separate draft model |
| N-gram | Lightweight | No extra model needed |
| Suffix Decoding | No extra model | Dynamic speculation depth |
| Dynamic SD | Variable workloads | Adjusts speculation depth |

**Key metrics**:
- `vllm:spec_decode_num_accepted_tokens_per_pos` (Counter) — acceptance rate by position
- Legacy metrics: `spec_decode_draft_acceptance_rate`, `spec_decode_efficiency`, `spec_decode_num_emitted_tokens`

**Configuration**:
```json
--speculative-config '{
  "method": "draft_model",
  "model": "<draft-model>",
  "num_speculative_tokens": 5
}'
```

**Latency diagnosis**:
- Low acceptance rate → draft model poorly matched to target
- High QPS → speculative decoding may not help (batch already saturated)
- Monitor `spec_decode_num_accepted_tokens_per_pos` — acceptance drops at higher positions
- Pipeline parallelism incompatible with speculative decoding (v≤0.15.0)
- Draft model memory overhead reduces KV cache available for main model

## 6. KV Cache Management

**What**: vLLM's KV cache manager tracks block allocation, eviction (LRU), and reference counting. Free blocks form a doubly-linked list for O(1) head/tail operations. Evicted blocks are returned to the free queue in reverse order (last block freed first, since it's least likely to be reused).

**Latency impact**: Efficient cache management prevents preemptions (which cause full re-prefill) and maximizes prefix cache hits.

**Key metrics**:
- `vllm:kv_cache_usage_perc` — primary indicator
- `vllm:kv_block_lifetime_seconds` — allocation to eviction
- `vllm:kv_block_idle_before_evict_seconds` — last touch to eviction
- `vllm:kv_block_reuse_gap_seconds` — gaps between block accesses

**Latency diagnosis**:
- Use KV block metrics to identify "stranded" cache (high lifetime, high idle)
- If `kv_block_reuse_gap_seconds` is high → blocks are being evicted before reuse
- Increase `gpu_memory_utilization` or reduce `max_model_len` for more headroom
- Preemptions (`vllm:num_preemptions`) are the most expensive latency event

## 7. Chunked Prefill

**What**: Splits long prefill computations across multiple forward passes, interleaving prefill tokens with decode tokens. This prevents long prompts from blocking the decode of other requests in the batch.

**Latency impact**: Improves ITL stability under mixed workloads (some long prompts + many decode requests). Trades slightly higher TTFT for much lower ITL variance.

**Metrics**:
- `vllm:request_prefill_time_seconds` — may increase with chunked prefill
- `vllm:inter_token_latency_seconds` — should decrease / stabilize
- `vllm:iteration_tokens_total` (Histogram) — tokens per engine step (reveals batch mixing)

**Latency diagnosis**:
- If ITL spikes correlate with new request arrivals → chunked prefill may not be active
- Check `iteration_tokens_total` distribution — healthy chunked prefill shows mixed token counts
- The V1 engine core runs a continuous busy loop that naturally handles this

## 8. Production Monitoring Stack

**Prometheus endpoint**: `GET /metrics` on the vLLM server

**Essential latency dashboard metrics**:
1. `vllm:time_to_first_token_seconds` — TTFT histogram
2. `vllm:inter_token_latency_seconds` — ITL histogram
3. `vllm:e2e_request_latency_seconds` — end-to-end latency
4. `vllm:request_prefill_time_seconds` — prefill phase time
5. `vllm:request_decode_time_seconds` — decode phase time
6. `vllm:num_requests_running` + `_waiting` — batch occupancy
7. `vllm:kv_cache_usage_perc` — memory pressure
8. `vllm:prefix_cache_hits` / `_queries` — cache effectiveness
9. `vllm:num_preemptions` — preemption events

**Per-request metrics** (enable with `--enable-per-request-metrics`):
- `time_to_first_token_ms`, `generation_time_ms`, `queue_time_ms`, `mean_itl_ms`, `tokens_per_second`

**PromQL examples**:
- Prefix cache hit rate: `rate(vllm:prefix_cache_hits[5m]) / rate(vllm:prefix_cache_queries[5m])`
- Saturation detection: `vllm:num_requests_running / (vllm:num_requests_running + vllm:num_requests_waiting)`
